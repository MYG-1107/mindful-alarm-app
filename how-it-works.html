01 · THE PROBLEM

What problem is ZenTimer designed to solve?

Many people can start a timer. The harder problem is maintaining a complete routine without repeated setup, noisy interruptions, context switching, or unnecessary data collection.

A

Manual context switching

A morning routine may need meditation, breathwork and journaling; a study block may alternate work and recovery. Recreating every timer adds friction.

B

Attention-breaking alerts

Long sessions need time awareness, but an aggressive alarm can become the interruption it was supposed to prevent.

C

Quiet environments

Libraries, shared offices and classrooms may not allow loud alerts. People still need a reliable visual completion signal.

D

Progress without a data cloud

Habit history is useful, but personal routines and notes do not need to leave the device just to show a streak or export a log.

03 · TECHNICAL ARCHITECTURE

What is happening underneath the interface?

The project deliberately uses browser-native capabilities so it stays easy to inspect, deploy and run as a static GitHub Pages application.

UI layerHTML + CSS

Responsive dashboard, routine builder, reflection modal, Zen Mode and accessibility-focused controls.

Timing engineWeb Worker

Runs the countdown independently from the main UI thread and advances stages and loops from timestamp calculations.

Audio engineWeb Audio API

Creates procedural ambient noise, a 432/436 Hz stereo tone pair and gentle chimes without a streaming service.

Local dataIndexedDB

Stores sessions, routines, streak data and the selected custom audio Blob in the browser.

Offline layerPWA + Service Worker

Caches the application shell so the app can launch offline after the service worker has installed its cache.

Device capabilitiesBrowser APIs

Optional Notifications, Media Session and Screen Wake Lock extend the experience where the browser supports them.

06 · ADVANCEMENT ROADMAP

What would turn this into a stronger production system?

These are future directions, not claims that the current version already supports them.

PHASE 1 · PRODUCT FOUNDATION

Routine intelligence

Routine favorites, duplicate/edit actions, named presets, scheduled routines and better cross-session summaries.

PHASE 2 · PERSONALIZATION

Adaptive sessions

Let users set goals such as “protect a 90-minute focus window” and generate a suitable block plan from their own saved patterns.

PHASE 3 · MOBILE

Companion app shell

Wrap the web experience for Android/iOS when stronger background guarantees, richer notifications or hardware integrations are required.

PHASE 4 · INTEROPERABILITY

Calendar & knowledge tools

Optional calendar import and export connectors, plus first-class formats for Obsidian, Notion and standard calendar files.

PHASE 5 · PRIVACY

Optional encrypted sync

A future opt-in sync layer could use end-to-end encryption so users can move routines between devices without making the local-first mode disappear.

PHASE 6 · QUALITY

Production-grade reliability

Add automated browser tests, accessibility audits, storage migration tests, telemetry-free diagnostics and explicit platform capability checks.

07 · VALIDATOR NOTES

What this system can—and cannot—promise.

Can do

Run structured timed routines, keep local progress, work from cached app files after installation, offer multiple completion modes, and export user-created session records.

Depends on the browser

Notifications, Wake Lock, Media Session, audio behavior and install prompts vary by browser and device. A browser page is not equivalent to a native alarm service.

Not safety-critical

Do not use the web timer as the sole mechanism for medical, emergency, industrial or other safety-critical timing requirements.

Not medical treatment

The app supports mindfulness and focus routines; it does not diagnose, treat or replace professional medical or mental-health care.
